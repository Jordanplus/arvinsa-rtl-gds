### 最重要的 5 項

1. **golden README 的 clock 一列過期，而且 skew 數字的意思容易被誤讀**（A53、S24）。
   - README 寫「兩個葉端 latency 差約 2 ns，成因沒有查」。`runs/p7_skew_analysis/README.md` 已經分析：−3.598 ns 中約 2.7 ns 是 `report_clock_skew -hold` 的算法（把 Caravel source latency 上下限差與共同路徑 derate 當扣分），真正影響 hold 的 skew 是 −0.632 ns，和 soc_top 的 −0.678 ns 差不多。
   - 這份分析把「2.7 ns 是報表算法」標成推測，也還沒寫回任何受版控的文件；寫回時要照實標推測。
   - `clock__skew__worst_hold` 這個彙總 metric 是各 corner 取最大（最不負），golden 裡是 −2.589；最差的 corner 是 max_ss_n40C −3.649；README 引的 −3.598 是 nom_ss_n40C。引用時要寫 corner，不能拿彙總值當最差值。
2. **IR 的說法在多份文件裡還停在已取消的判法，或把不同條件的數字放在一起比**（S30、A21、S31、S12、S14、S09、A20）。
   - 流程文件:194 與 ADR 決定 19（第 102 行，50 mV）仍寫供電要求或 50 mV；決定 20 已改成 max power pattern、20 mV（上限檔 `max = 0.02`）。
   - 「wrapper ring 會低估 5 倍以上（8.4 → 45 mV）」：8.4 是 ff 電流＋ss 電阻的最壞組合、met4 1.6 µm、ring 供電；45 是慢 corner、met4 4.8 µm、從 pad 起算。同條件比是 4.94 → 45.56 mV。
   - chip-floorplan skill 的「整圈 6.87、只從上側 143 mV」沒寫是已否決的最壞組合，而且拿去對 20 mV 上限；規則 2「怎麼估」還教用最壞組合。照這條估會得到很悲觀的值，Phase 7 就是被這個帶去考慮移 block。
3. **golden README 的出處欄自相矛盾**（A51、A61、A50）。
   - 第 14、39 行說來源是 `f721cff`，第 42 行說 `7eff65a`「本檔現在的來源」，兩列都說自己是「本檔來源」。
   - 「與 `p7_exp_pl_dens` 共有的 429 個逐值相同」只對建立時的版本成立；對現在的 golden 是 425 個相同、4 個不同（fill 數、instance 數、leakage、power）。
   - 「步驟 8 兩個乾淨 worktree 跑完後修正誤差」已被決定 25 改成一條 `regress-caravel` 加先前同機 4 次 run。
4. **證據路徑指向已被覆蓋的目錄**（S22、S23）。knowledge 檔 2026-10-13／14 的幾列引用 `runs/user_project_wrapper_signoff/criteria_review.md`，這個檔現在是 550869c 的 review，裡面沒有那些數字。數字實際在 `runs/p7_formal_signoff/`、`runs/p7_decap_signoff/`。golden README 已經用另存目錄，knowledge 檔沒有。
5. **寫了要加、但實際沒加的防護**（S36），以及計數不一致（A33、S23）。
   - `timing-constraints-sdc` 規則 14 寫「Phase 7 第 5 項加一列比對腳位 slew」，結案時沒有加。`check_soc.py` 只把 SDC 的 transition 當放寬的上限；如果 driving cell 再把 `set_input_transition` 蓋掉，腳位 slew 會變小，checker 仍判 PASS。這是真的防護缺口，應改成「沒有自動防護＋原因」，或補上這一列。
   - `decap_3` 的數量有兩個值交替出現：ADR:167、筆記:133、config 註解、knowledge 檔寫 2,461,688（網表總數，含 2,904 個 row 兩端的 endcap）；golden README 與 decap 的 criteria review 寫 2,458,784（Fill Insertion 放的）。兩者都對，但沒有任何一處說明差別。
