## 決定

1. **`wb_rst_i` 的描述：修正，並把 Caravel reset 的實際行為和影響寫成紀錄**。
   - 問題：
     - ADR-0019 決定 8（第 31 行）寫「`wb_rst_i` 由管理用 SoC 在 `wb_clk_i` 下產生」；
     - `rtl/caravel/wb_host_bridge.v` 第 25 行寫「synchronous to clk」，`caravel_io.sdc` 第 22 行寫「generated by the management SoC on wb_clk_i」（這一項的行號都是修改前的）；
     - ADR-0019 第 60 行與 `caravel_io.sdc` 第 2–4 行，把 `wb_rst_i` 的半週期 input delay 說成從 Caravel 的 STA 抽出。
   - 查證結論（筆記第 1–3 節）：
     - `wb_rst_i` 由 `caravel_clocking` 裡的 3 級 reset synchronizer 產生，管理用 SoC 只是收到同一個 reset。POR、`resetb` pad、housekeeping 的 reset 暫存器或 SPI pass-through 任一個有效時立刻拉起（非同步）；全部放開後，在核心時脈（就是 `wb_clk_i`）的第 3 個下降緣放開；再經 `mgmt_protect` 反相（Caravel `caravel_clocking.v` 第 51、101–112 行；`housekeeping.v` 第 254 行；`mgmt_protect.v` 第 232 行；`caravel_core.v` 第 410、444、534 行）。
     - 放開由 STA 用半週期檢查，而且有加上 4.65–5.57 ns 的 source latency。沒算進去的只有 Caravel 內部 reset 路徑與時脈路徑的延遲差，以及最多 2.2 ns 的 duty cycle 偏差。signoff 的 setup／hold 違規數都是 0，這條路徑的 slack 至少 +0.548 ns；粗估的實際 slack 有十幾 ns（推測）。
     - 拉起是非同步的，STA 不檢查。`resetn` 經組合邏輯接到 SRAM 的 `csb0`（`rtl/bus/soc_bus.v` 第 229、241 行），所以規格 §4.9 的 RTL-RST-01 在晶片上不保證；本設計 reset 後由管理用韌體重新載入 SRAM，沒有長期影響（推論）。
     - 另外三點都是推論：reset 最短只有 2 個上升緣，但要 reset 來源短於一個時脈才會發生；韌體啟用 PLL 之後，POR 以外的來源（`resetb` pad、reset 暫存器、SPI pass-through）觸發的 reset 會讓核心時脈經一般的 mux 切換；`vccd1` 在 Caravel 的 reset 放開之後才上電時，wrapper 收不到 reset。
     - 半週期 input delay 在官方 SDC 前半手寫的「Pre-defined Constraints」段（caravel_user_project `b510613` `openlane/user_project_wrapper/signoff.sdc` 第 11、52–53 行），不在從 STA 抽出的「Retrieved Constraints」段（第 64 行起）。
     - 結論：這是文件寫錯，不影響本設計的設計與時序，不用重新 harden。
   - 選項：
     - A：只改錯誤與不精確的說法（ADR-0019 加更正註記、改兩個檔的註解）；
     - **B：做 A，再把 Caravel reset 的實際行為和影響寫成紀錄（建議）**；
     - C：做 B，再在 Caravel 版 testbench 補 directed test（RTL 模擬是零延遲，證明不了非同步拉起的問題；`make regress-caravel` 約 7 小時）；
     - D：先重新 harden，讀出 `wb_rst_i` 路徑的 slack 再決定（數小時，讀出來的數字幾乎不可能改變選擇）；
     - E：改 RTL，在 wrapper 內對 `wb_rst_i` 加 2 顆 flop 的同步器（lint、DV、EQY、harden、regress 約 10 小時以上；本專案不下線，改了也不會用在晶片上）。

2. **管理端時脈上限：更正 ADR 與報告，寫清楚三個數字各代表什麼**。
   - 問題：ADR-0019 決定 15（第 66 行）寫「Caravel 文件寫核心時脈上限『TBD，約 50 MHz』」，沒附出處。技術報告 §9.1（英文第 1917 行、中文第 1659 行）照抄，和同一份報告 §3.4（英文第 299 行、中文第 319 行）的 40 MHz 矛盾。
   - 查證結論（筆記第 5 節）：
     - 約 50 MHz：出自 PicoRV32 時期的 Caravel 文件（efabless/caravel `e5cf492` 的 `docs/source/description.rst`，2021-12-17），自己標 TBD；同一天的 `ee7eded` 改成「TO BE UPDATED」，現行 `27cbe49c` 也是。不能引用。
     - 40 MHz：Caravel 對 `caravel_core` 做 signoff 用的時脈（`27cbe49c` `signoff/caravel_core/caravel_core.sdc` 第 7–8 行，25 ns），VexRiscv 管理用 SoC（CPU 名稱見 `.tools/caravel-lite` 的 `verilog/gl/caravel_core.v` 第 20207 行起的 `soc.core.VexRiscv.*` net 名稱）自己 harden 時也用 25 ns（caravel_mgmt_soc_litex `openlane/mgmt_core_wrapper/config.tcl` 第 22 行），文件表格也寫 40 MHz（`docs/source/maximum-ratings.rst` 第 40 行）。這是設計目標。
     - 33 MHz：正式 datasheet CARAVEL-001 §3.2 的操作條件（0–70 °C；`27cbe49c` `docs/caravel_datasheet_2.pdf` 第 11 頁）。這是保證值，最保守。
     - 對本設計：signoff 在 44 ns（22.7 MHz），比三個數字都慢，signoff 結論與「管理端時脈 ≤ 22.7 MHz」都不變。真的跑在 40／50 MHz 時，整週期路徑約差 18／23 ns，SRAM 半週期路徑約差 8.4／10.6 ns（推估，沒有跑 STA）。44 ns 本身也幾乎沒有空間：半週期路徑最短約 43.7 ns（推估）。
   - 選項：
     - **1：更正 ADR 與報告，寫清楚三個數字各代表什麼（建議）**；
     - 2：選項 1，再把 Caravel 管理端時脈上限寫回 `caravel-user-project-integration` 規則 2（多約 20–30 分鐘，要同步 README）；
     - 3：只改成 40 MHz，不提 datasheet 的 33 MHz；
     - 4：先跑 STA what-if（25 ns、20 ns）再決定（harden 約 4.3 小時，跑完不會改變決定）；
     - 5：維持原文。
   - 使用者 2026-10-16：「1：更正 ADR 與報告 (建議)」。提問時列出 1、2、3、5 四項；4 只寫在查證結果裡，沒有放進提問。
   - 決定與要改的檔案：
     - 這次完成：ADR-0019 第 66 行加 2026-10-16 的更正註記，不改原文。
     - 同一個 commit 一起完成：技術報告英文第 1917 行、中文第 1659 行改成同樣的內容；英文第 299 行、中文第 319 行在 40 MHz 後面補上 Caravel signoff 的 25 ns 與 datasheet 的 33 MHz；重建兩份 PDF。

3. **GPIO 33–37：管理用韌體的 GPIO 設定傳送寫進文件與 skill，不做新的 checker**。
   - 問題：技術報告 §3.4（中文第 357 行、英文第 337 行）寫到，韌體啟動一次 GPIO 設定傳送後 33–37 會變回 management mode；這段標成推論、沒有模擬確認，也沒寫每支腳受的影響與怎麼恢復。§9.1、Phase 7 已知限制與 skill 都沒有這條韌體限制。§3.4 第 354 行（英文第 334 行）「不必等 management SoC 的韌體設定」也要加條件。
   - 查證結論（`docs/notes/caravel_gpio_xfer.md`）：
     - 原因：housekeeping 自己存的 GPIO 設定，reset 值是 management mode（33–35 是 `0x0403`，36–37 是 `0x1803`；Caravel `housekeeping.v` 第 1061–1071 行），只有 POR 會重置（第 1031 行）。一次傳送會覆蓋 38 支腳的設定。本設計兩份值不同的只有 33–37（`rtl/caravel/user_defines.v` 第 92–96 行設成 user mode）。gate-level netlist 的 reset 值和 RTL 相同。
     - 用 Caravel RTL、本專案的 `user_defines.v` 與假的 management core 做非正式的模擬（證據在 `docs/evidence/arvinsa-rtl-gds/runs/p7_gpio_xfer/`）：
       - 只設 5、6 就傳送：`uart_tx`（37）、`trap`（35）到不了腳位；`uart_rx`（36）、`boot_mode`（33、34）的輸入仍送得到 user area，但 33、34 的內部下拉沒了，板子沒接線時 `boot_mode` 浮接，boot ROM 的開機方式無法確定；
       - 先把 33–37 寫回 user mode 再傳送：維持 user mode；不傳送：一直是 user mode；
       - 用 bit-bang 把 `serial_resetn` 拉低一次可以恢復，38 支都還原成開機預設（`housekeeping.v` 第 908–911、1137–1138 行）；拉 `resetb` 救不回來。
     - 管理用韌體打開 QSPI 時，36 可能和外部的 UART TX 互相驅動（只依原始碼，推測）。
     - repo 的模擬只到 wrapper，沒有 management core，驗不到這件事。
     - 本專案不下線；韌體在外部 SPI flash，重燒就能修。這顆設計的管理用韌體其實不需要做傳送（推論）。
   - 選項：
     - **A：寫回文件與 skill，不做新的 checker（建議，修正版）**；
     - B：做 A，再把實驗做成 repo 內 self-checking 的 regression test（0.5–1 個工作天）；
     - C：用官方 caravel-cocotb、真的 management SoC 與韌體做全晶片模擬（2–4 個工作天，要網路與 Docker）；
     - D：維持現狀（不符合 CLAUDE.md 規則 2：任務做完要寫經驗紀錄）。
   - 使用者 2026-10-16：「A：寫進文件與 skill (建議)」。
   - 決定與要改的檔案，全部同一個 commit 一起完成：
     - 兩份技術報告：
       - §3.4 第 357 行（英文第 337 行）改成模擬確認的結果，寫出每支腳受的影響、`resetb` 救不回來與三種恢復方法（重新上電、用正確的設定再傳一次、bit-bang 拉低 `serial_resetn`）；QSPI 那點標明「只依原始碼」；
